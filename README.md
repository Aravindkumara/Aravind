# OEM Product Service Excellence

A web application for defining **standard operating procedures (SOPs) for product service activities at dealer workshops**.
SOPs are classified by **division → model category → model → variant → assembly level**, go through an authoring and approval workflow, and are published to dealers. Dealers find the procedures that apply to the vehicle they are working on.

| Layer      | Technology |
|------------|------------|
| Frontend   | ASP.NET Core MVC (.NET 8), Bootstrap 5, jQuery validation |
| Backend    | ASP.NET Core Web API (.NET 8), JWT bearer auth, Swagger, Serilog |
| Data layer | Dapper + Npgsql (hand-written SQL, no ORM) |
| Database   | PostgreSQL 16 |
| PDF        | QuestPDF |

## Features

**Product hierarchy (master data)**
- Divisions, model categories, models and variants, each linked to its parent.
- Assemblies per variant in three levels: **Assembly → Sub-assembly → Component**, shown as a tree.

**SOP authoring**
- An SOP has a code, title, service activity (PDI, Periodic Maintenance, Repair, Inspection/Diagnosis, Warranty, Campaign/Recall), purpose, standard labour time, skill level and safety precautions.
- An SOP can be attached at **any level** of the hierarchy. An SOP for a whole model applies to all its variants and assemblies.
- Steps are ordered and can be moved up or down. Each step has an instruction, tools, a specification/torque value, a caution, an estimated time and **attachments** (JPG/PNG/GIF/WEBP/PDF, up to 10 MB).
- Each SOP lists the **parts, special tools and consumables** it needs, with quantities.

**Workflow and versioning**
- `Draft → Under Review → Approved → Published`. A reviewer can reject an SOP back to the author with remarks, and a published SOP can later be marked `Obsolete`.
- Approvers cannot approve or reject an SOP they wrote themselves. Administrators are exempt from this rule.
- **New version** copies a published SOP, including its steps, resources and attachments, into a new draft. Publishing it makes the previous version obsolete automatically.
- Only `Draft` and `Rejected` SOPs can be edited.

**Dealer SOP Finder**
- A dealer picks Division → Category → Model → Variant → Assembly and gets every **published** SOP that applies. That includes SOPs defined at higher levels, and for a selected assembly, SOPs on its parent and child assemblies.
- Dealers never see unpublished SOPs, through the UI or the API.

**Output and traceability**
- **PDF export** (A4, generated by the API) with embedded step photos and sign-off boxes, plus a printer-friendly HTML view.
- **Audit trail** of every create, update and workflow action. Each SOP page shows its own history, and admins get a global audit page with filters.

**Cross-cutting**
- Login with JWT and **role-based access**.
- Server-side **search, paging and sorting** on every list.
- **Swagger** UI, structured logging with **Serilog** (console and rolling files), and **global error handling** that returns RFC 7807 problem details.

### Roles

| Role       | Can do |
|------------|--------|
| `Admin`    | Everything: manage users, dealers and master data, author and approve SOPs, view the audit trail |
| `Author`   | Create and edit draft SOPs, submit them for review, create new versions |
| `Approver` | Approve, reject, publish and obsolete SOPs written by others |
| `Dealer`   | Read published SOPs (SOP Finder, SOP Library, print/PDF) |

## Getting started

### Option 1: Docker (recommended)

```bash
docker compose up --build
```

| URL | What |
|-----|------|
| http://localhost:8080 | Web application (MVC) |
| http://localhost:8081/swagger | Web API / Swagger UI |
| `localhost:5433` | PostgreSQL (`service_excellence` / `sopapp` / `sopapp_pwd`) |

The schema and sample data in `database/` load automatically the first time the database volume is created. To reset everything, run `docker compose down -v`.
For anything beyond local use, set `JWT_KEY` and `POSTGRES_PASSWORD` in the environment or in a `.env` file.

### Option 2: Run locally

Prerequisites: .NET 8 SDK and PostgreSQL 14 or newer.

```bash
# 1. Create the database and load schema + sample data
psql -U postgres -c "CREATE USER sopapp WITH PASSWORD 'sopapp_pwd';"
psql -U postgres -c "CREATE DATABASE service_excellence OWNER sopapp;"
psql -U sopapp -d service_excellence -f database/01_schema.sql -f database/02_seed.sql

# 2. Start the API (http://localhost:5100/swagger)
dotnet run --project src/ServiceExcellence.Api

# 3. Start the MVC frontend in another terminal (http://localhost:5000)
dotnet run --project src/ServiceExcellence.Web
```

### Sample users

All sample users have the password **`Pass@123`**. Change it after the first login.

| Username   | Role     |
|------------|----------|
| `admin`    | Admin    |
| `author`   | Author   |
| `approver` | Approver |
| `dealer`   | Dealer (Prime Motors Bengaluru) |

The sample data includes three divisions, variants with an assembly tree, and three SOPs: a division-level PDI, an assembly-level oil service, and a draft injector replacement.

## Solution structure

```
ServiceExcellence.sln
├── database/
│   ├── 01_schema.sql              # tables, constraints, indexes
│   └── 02_seed.sql                # sample data
├── src/
│   ├── ServiceExcellence.Core/    # constants, DTOs (shared by API and MVC), repository interfaces
│   ├── ServiceExcellence.Data/    # Dapper repositories (PostgreSQL)
│   ├── ServiceExcellence.Api/     # Web API: controllers, services (workflow, PDF, files, audit), JWT, Swagger
│   └── ServiceExcellence.Web/     # MVC frontend: controllers, Razor views, typed API client
└── docker-compose.yml
```

How a request flows:

```
Browser ──cookie──▶ MVC (ServiceExcellence.Web) ──HTTP + JWT──▶ Web API ──Dapper──▶ PostgreSQL
                         ApiClient + BearerTokenHandler           SopService            repositories
```

- The MVC app has no database access. It calls the API through `ApiClient`. At login it receives the JWT from `POST /api/auth/login` and keeps it inside its own HttpOnly authentication cookie, and `BearerTokenHandler` adds it to every API call.
- Business rules (classification consistency, workflow transitions, edit locks, the reviewer-is-not-author rule, attachment validation, audit) live in the API's `SopService`, so they hold for any API client.
- Repositories use parameterised SQL. Sortable columns come from per-repository whitelists, so user input never reaches the SQL text.

## Main API endpoints

| Method & route | Purpose |
|----------------|---------|
| `POST /api/auth/login` | Get a JWT |
| `GET /api/masters/{Division\|Category\|Model\|Variant}` | Search, page and sort master data (`?search=&parentId=&page=&pageSize=&sortBy=&sortDir=`) |
| `GET /api/masters/{type}/lookup?parentId=` | Drop-down data |
| `GET /api/assemblies/tree?variantId=` | Assembly tree of a variant |
| `GET /api/sops` | Search SOPs (`status`, `activityType`, `divisionId`, …) |
| `GET /api/sops/finder?variantId=&assemblyId=` | Published SOPs applicable to a product |
| `GET/POST/PUT/DELETE /api/sops/{id}` | SOP header |
| `POST /api/sops/{id}/{submit\|approve\|reject\|publish\|obsolete\|new-version}` | Workflow |
| `/api/sops/{id}/steps[/{stepId}[/move]]` | Steps |
| `POST /api/sops/{id}/steps/{stepId}/attachments` | Upload an attachment (multipart, field `file`) |
| `/api/sops/{id}/resources` | Parts, tools and consumables |
| `GET /api/sops/{id}/pdf` | PDF export |
| `GET /api/sops/{id}/history`, `GET /api/audit` | Audit trail |
| `/api/users`, `/api/dealers` | Administration |

Full documentation is in Swagger.

## Configuration

| Setting (API) | Description |
|---------------|-------------|
| `ConnectionStrings:Default` | PostgreSQL connection string |
| `Jwt:Key` | HMAC signing key, at least 32 characters. **Change it for any shared environment.** |
| `Jwt:ExpiryMinutes` | Token and session lifetime (default 480) |
| `Storage:UploadPath` | Folder for attachments (a Docker volume in compose) |
| `Storage:MaxFileSizeBytes` | Upload size limit (default 10 MB) |
| `Swagger:Enabled` | Expose Swagger UI |

| Setting (Web) | Description |
|---------------|-------------|
| `Api:BaseUrl` | Base URL of the Web API |

Logs are written to the console and to `logs/` (rolling daily, 14 days kept) by Serilog.
Environment variables override settings in the usual ASP.NET Core way, e.g. `ConnectionStrings__Default`.

> **Licensing note:** QuestPDF is used under its Community licence, which is free for organisations with less than USD 1M annual gross revenue. Larger companies need a QuestPDF commercial licence. If that is a problem, the PDF generator can be replaced, and the browser print view works without it.
